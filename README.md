# Transactions Service

A small REST service that manages cardholder **accounts** and their **transactions**.
Each transaction belongs to an account and has an operation type. The service enforces
the amount sign based on that type: purchases and withdrawals are stored as **negative**
amounts, credit vouchers as **positive**.

## Tech Stack

| Concern      | Choice                                                |
|--------------|-------------------------------------------------------|
| Language     | Java 21 (LTS)                                         |
| Framework    | Spring Boot 3.5.x                                     |
| Build        | Maven (via wrapper — no local Maven install needed)   |
| Persistence  | Spring Data JPA / Hibernate                           |
| Migrations   | Flyway                                                |
| Database     | H2 in-memory (default) · PostgreSQL (Docker profile)  |
| Testing      | JUnit 5, Mockito, MockMvc                             |

## Prerequisites

- **Local run:** Java 21+ only (Maven is bundled via `./mvnw`).
- **Docker run:** Docker + Docker Compose. No Java needed on the host.

## Running

A single script handles every mode:

```bash
chmod +x run.sh     # first time only
./run.sh            # local, in-memory H2 (default)
./run.sh docker     # PostgreSQL via Docker Compose
./run.sh test       # run the full test suite
```

The app starts on `http://localhost:8080`.
In local mode, the H2 console is at `http://localhost:8080/h2-console`
(JDBC URL `jdbc:h2:mem:transactionsdb`, user `sa`, no password).

## API Reference

### Create an account — `POST /accounts`

```bash
curl -X POST http://localhost:8080/accounts \
  -H "Content-Type: application/json" \
  -d '{"document_number": "12345678900"}'
```

`201 Created`
```json
{ "account_id": 1, "document_number": "12345678900" }
```

Errors: `400` if `document_number` is missing or blank · `409` if it already exists.

### Get an account — `GET /accounts/{accountId}`

```bash
curl http://localhost:8080/accounts/1
```

`200 OK`
```json
{ "account_id": 1, "document_number": "12345678900" }
```

Errors: `404` if the account does not exist.

### Create a transaction — `POST /transactions`

```bash
curl -X POST http://localhost:8080/transactions \
  -H "Content-Type: application/json" \
  -d '{"account_id": 1, "operation_type_id": 1, "amount": 50.00}'
```

`201 Created`
```json
{
  "transaction_id": 1,
  "account_id": 1,
  "operation_type_id": 1,
  "amount": -50.00,
  "event_date": "2025-01-01T10:00:00Z"
}
```

The client always sends a **positive** `amount`; the service applies the sign.
`event_date` is set server-side (UTC), never accepted from the client.

Errors: `400` on validation failure · `404` if the account or operation type does not exist.

### Operation types (seeded)

| ID | Description                | Stored amount |
|----|----------------------------|---------------|
| 1  | Normal Purchase            | negative      |
| 2  | Purchase with installments | negative      |
| 3  | Withdrawal                 | negative      |
| 4  | Credit Voucher             | positive      |

### Error response shape

All errors share one structure; field-level detail appears only on validation failures:

```json
{
  "status": 400,
  "error": "Bad Request",
  "message": "Validation failed",
  "timestamp": "2025-01-01T10:00:00Z",
  "errors": { "amount": "Amount must be a positive value" }
}
```

## Data Model

```
accounts(account_id PK, document_number UNIQUE)
operation_types(operation_type_id PK, description, requires_negative)
transactions(transaction_id PK, account_id FK, operation_type_id FK, amount, event_date)
```

Schema and seed data are managed by Flyway (`src/main/resources/db/migration`):
`V1` creates tables, `V2` seeds operation types, `V3` adds the `requires_negative` flag.

## Design Notes

- **Layered architecture** (controller → service → repository) keeps HTTP, business
  logic, and persistence separate and independently testable.
- **Sign logic lives in the service layer** and is *data-driven* via the
  `requires_negative` column rather than hardcoded IDs — adding a new operation type
  needs no code change.
- **Records for DTOs** (immutable, no boilerplate); mutable entities for JPA, which
  requires a no-arg constructor and setters.
- **`BigDecimal` for money** (exact) and **`Instant` for time** (always UTC).
- **`ddl-auto=validate`**: Hibernate validates entities against the Flyway schema on
  startup, so the model and migrations can never silently drift.
- **Cross-database SQL**: the migrations use only syntax common to H2 and PostgreSQL
  (`GENERATED BY DEFAULT AS IDENTITY`, `TIMESTAMP WITH TIME ZONE`, `DECIMAL`), so they
  run unmodified against both.
- A **global exception handler** maps domain exceptions to consistent HTTP responses
  (404 / 409 / 400 / 500).

## Project Structure

```
src/main/java/com/visa/transactionapplication/
├── controller/   # REST endpoints (thin)
├── service/      # business logic + sign enforcement
├── repository/   # Spring Data JPA interfaces
├── entity/       # JPA entities
├── dto/          # request/response records
└── exception/    # domain exceptions + global handler

src/main/resources/db/migration/   # Flyway V1–V3
src/test/java/.../                  # *Test (unit) + *IT (integration)
```

## Testing

```bash
./run.sh test     # or: ./mvnw test
```

Unit tests (`*Test`) exercise the service layer in isolation with Mockito.
Integration tests (`*IT`) run the full stack against H2 via MockMvc.
